# A2141 温控与卡顿详解

> 适用机型：2019 款 16 英寸 MacBook Pro（型号 **A2141** / 机型标识 **MacBookPro16,1**，i9-9980HK + Radeon Pro 5500M）及同代 Intel 机型。
> 本文所有"实测"数据均来自这台机器（macOS 26.5，2026-09-07），验证脚本和方法在文末"诊断速查"。
> MacState v1.9.1 起的限速显示就是按本文的结论实现的。

---

## TL;DR

1. **"到 90°C 就卡"不是 90°C 温度墙。** Intel CPU 的硬性热保护（PROCHOT）在 **100°C**（Tjmax）才动作，Apple 没有改这个值；实测里限制在板级测点只有 58~65°C 时就触发了——**触发条件是功率爆发，不是温度数值**。
2. 真正掐住机器的是 **SMC 的功率限制（PLIMIT）**：负载功率一冲高（实测 125W），SMC 几秒内开始发 CPU/GPU 功率限制，而且**负载停止后钳制状态会维持几十分钟**。这就是"温度不高也卡"的原因。
3. 根源是 A2141 的**供电区（VRM）散热设计缺陷**：没有散热覆盖、SMC 也读不到它的温度。外网有大量实测报告（57W 功率墙、76°C 卡 1.8GHz 等），Apple 从未官方承认。
4. MacState v1.9.1 已把限速显示纠正为**瞬时 PLIMIT**，并新增 GPU 限制显示——这个数字才是判断"现在卡不卡"的可靠依据。

## 1. 名词解释：这台机器里谁在管温度和功率

### 1.1 SMC 是什么

**SMC（System Management Controller，系统管理控制器）** 是 Mac 里一颗独立的微控制器芯片（在带 T2 的机型上是 T2 芯片的一部分），跑着自己的固件，**独立于 macOS 运行**。它负责：

- 全部风扇的转速控制；
- 读取几十个温度传感器（CPU/GPU 附近的"测点"、热管、进风口、外壳、电池……）；
- **决定整个机器允许消耗多少功率**（本文的主角 PLIMIT 就是它发的）；
- 电池充放电管理、键盘背光、开盖开机等等。

macOS（以及 MacState 这类软件）通过 IOKit 的 `AppleSMC` 服务用"4 字符键名"读写它的数据，例如 `TC0P` = "CPU 供电区近旁的板级温度"、`PCPC` = "CPU 封装功率"、`MSAc` = "SMC 发过的 CPU 限制的滚动平均"。

关键理解：**SMC 是一台"黑盒控制器"**。它固件里的决策逻辑（什么温度/什么功率触发什么限制）没有公开文档，我们只能观察到它的输入（部分传感器）和输出（PLIMIT、风扇转速）。

### 1.2 VRM 是什么

**VRM（Voltage Regulator Module，供电模块）** 是主板上把 20V（适配器）/12V（电池）转换成 CPU 和 GPU 用的 ~1V 大电流的电路，由 PWM 控制芯片、若干"供电相"（功率 MOSFET + 电感）和电容组成。

为什么它会成为瓶颈：

- 转换效率不是 100%，**电流越大发热越大**（I²R 损耗）。给 CPU 供 40A 电流时哪怕 90% 效率也有 4~5W 热耗在一小块硅和电感上；
- A2141 的 VRM **没有焊在任何散热片上**，只能靠风扇吹过主板带走热量；
- 它的温度**没有任何传感器暴露给 SMC**（MacState 的"供电 / VRM"组显示的是供电区*旁边*的板级测点 `TC0P`/`TGVP`，不是 VRM 结温）。

### 1.3 其他会在本文出现的名词

| 名词 | 含义 |
|---|---|
| **Tjmax / PROCHOT** | CPU 的结温上限（9980HK = 100°C）。任一核心到 100°C，CPU 硬件直接钳频保命，与操作系统无关 |
| **TCC offset** | 允许系统把 PROCHOT 提前到低于 Tjmax 的偏移量。外网 MSR 转储显示 Apple 设的是 0（即不提前） |
| **PLIMIT** | SMC 下发的功率限制指令，按 CPU/GPU/内存三个域分别给一个百分比。MacState 读的就是它 |
| **MSAc** | SMC 的诊断键：它**历史上发过的** CPU PLIMIT 的滚动平均值（见 §3，容易被误读） |
| **XCPM** | macOS 内核的 Intel 电源管理子系统，管理频率墙和热压力分级 |
| **SFI / 热压力指数** | macOS 的"选择性强制空闲"机制：SMC/内核维护一个 0~255 的无量纲压力指数，指数越高，后台和 utility 类任务允许占用的算力越少 |
| **BD PROCHOT** | Intel 平台的一个外部信号脚：供电/电源管理等子系统可以拉低它强制 CPU 降频，**无需 CPU 本身过热**。Boot Camp 下用 HWiNFO 能直接看到它被触发 |

## 2. 这台机器的温控策略表（实测解码）

Apple 没有一份可读的"多少 °C 降频"文件，阈值映射烧在 SMC 固件里。以下是能从机器里实际解出来的全部策略数据（来源：`X86PlatformPlugin.kext` 里 A2141 的配置文件 + 运行时 ioreg + sysctl）：

| 项目 | 数值 | 说明 |
|---|---|---|
| CPU 硬性热保护 | **100°C** | Tjmax/PROCHOT，硬件行为，到点直接钳频 |
| CPU 频率墙 | 硬上限 4.9GHz / 软上限 5.0GHz / 下限 0.8GHz | `machdep.xcpm` 实测值 |
| 电池低电量模式频率上限 | 2.6GHz | 未开启时不生效 |
| 平台功耗档 | **10 / 25 / 35 / 45 / 55 / 65 / 100W** | 从配置二进制解出；45W=TDP 持续档，55~65W 短时睿频档，100W=适配器预算 |
| 强制限制时的性能地板 | CPU 42% / 核显 18% / 独显 15% | SMC 深度钳制时保底不把任务压死 |
| macOS 热压力分级 | Nominal 0–57 / Moderate 50–130 / Heavy 100–200 / Trapping 170–250 | 无量纲压力指数（非 °C）；utility 任务从 53 开始被压 |
| GPU（5500M）限温值 | **不可读** | SMC 不暴露；限制走 PLIMIT |

**注意表里没有任何一行是"90°C"** —— 实测降频触发点由功率/供电状态决定，温度只是伴随指标。

## 3. MacState 里"过热保护"的数据从哪来

| 界面 | 来源 | 说明 |
|---|---|---|
| 热状态（正常/轻微/偏高/严重） | `ProcessInfo.thermalState` | macOS 内核的热压力等级，四档 |
| **当前限制（CPU/GPU）** | SMC **PLIMIT 命令**（v1.9.1 起） | 瞬时值。0=不限，显示为 100% |
| 近期平均 | SMC 键 `MSAc` | ⚠️ 它是 SMC 发过的 PLIMIT 的**滚动平均**，不是瞬时值 |
| CPU/GPU/系统功率 | SMC 键 `PCPC` / `PCPG` / `PSTR` | 瓦特 |
| 供电/VRM 组温度 | SMC 板级测点 `TC0P`/`TGVP`/`TGVF` | 供电区**旁边**的板级温度，不是 VRM 结温 |

### `MSAc` 的坑（v1.9.0 及之前显示不准的原因）

权威键表（floe/smc_util）对 `MSAc` 的定义是 *"Returns the average CPU PLIMIT sent by the SMC"*——**历史均值**。后果是：

- 一次钳制结束后，`MSAc` 会把这个钳制值继续平均进去，**滞后显示几十分钟**（实测：钳制已恢复到 0，`MSAc` 还显示 31）；
- 长期没被钳制的机器上它接近 0，看起来像"限速 1%"，其实什么都没发生。

所以 v1.9.1 改成：**瞬时值用 PLIMIT 命令，`MSAc` 单独标注"近期平均"只作参考**。瞬时 PLIMIT 在钳制时几秒内就会跌下来（实测从 100% → 31% → 13% → 3% 的恢复轨迹清清楚楚），这才是能信的数字。

另有两个键位事实，排查时少走弯路：瞬时"最后一次 PLIMIT"键 `MSTc` 在 MBP16,1 上**不存在**（瞬时值只能走 PLIMIT 命令）；本机也没有 `TC0D`/`TC0c`/`TC1c`（CPU die 温度）、`TG0D`、`MSIm` 这些 x86 机型常见键——CPU 区域只有板级测点 `TC0P`，所以 MacState 显示的"CPU 温度"天然比真实结温低 15~25°C。

## 4. 实测：卡顿是怎么发生、怎么持续的

2026-09-07 在本机做的 8 核满载实验（`yes` × 8，95 秒），每秒记录 SMC：

**触发：功率爆发，而不是温度**

| 时间 | 系统输入功率 | CPU 功耗 | CPU 板级测点 TC0P | 现象 |
|---|---|---|---|---|
| 负载前 | 52W | 10W | 58°C | 未钳制（PLIMIT 无记录） |
| 负载 +3s | **124.9W** | 68.6W | 60°C | 功率爆发 |
| 负载 +10s | 111W | 57.8W | 62°C | SMC 开始发 PLIMIT |
| 负载 +40s | 66W | 19W | 62°C | **CPU 被压到 ~26% 允许功率** |

注意：TC0P 全程没超过 64°C——**限制发生时 CPU"温度"读数完全正常**。（CPU 真实结温比板级测点高 15~25°C，爆发时可能摸到 90~100°C，但那不是触发的判据。）

**持续：负载结束后钳制黏住不走**

负载停止后 **30+ 分钟**：

- PLIMIT 命令实测：**CPU=31%，GPU=7%**（独显被压到 7%！）
- CPU 功耗被按在 10~13W；风扇钉死 5600rpm
- macOS 显示 CPU_Speed_Limit=38%，热压力指数 139（Heavy 区间）
- 而所有可读温度只有 58~65°C

这 30 分钟里的体感就是用户说的"很卡"，且有两层可量化的证据：

- **进程级**：钳制期间 WindowServer（窗口合成器）占 78%、kernel_task 占 35%——CPU 被掐住后合成器抢不到算力，UI 掉帧；
- **基准级**：负载停止 15 秒后（钳制未解除时），单线程 sha256 吞吐仍比空闲基线低 ~30%（306MB/s → 214MB/s）——这就是"活干完了机器还是卡"的直接来源，与板级温度读数无关。

**恢复与再触发**

之后钳制缓慢松开（31% → 13% → 3% → 0，历时约 1 小时）。但浏览器把独显唤醒、系统功率再冲到 81W 时，**CPU PLIMIT 立刻又被打到 17~18%**。独显一亮、CPU 一忙就复发的特征非常明显（见 §6）。

## 5. 直接回答：SMC 读不到 VRM 温度，为什么还会压功率？

> "既然读不到温度，那系统是怎么知道该压功率的？"

**"没有温度传感器" ≠ "不知道供电侧出问题了"。** 压功率的决策不依赖"读 VRM 温度"这一条路，至少有三条别的信息通路：

**① VRM 自己会"喊疼"——硬件保护信号（主要机制）**

VRM 的控制芯片（PWM 控制器/Power Stage）**自带过温过流保护**：结温过高或电流超限时，它会自己降输出、限电流，并**通过平台信号直接通知 CPU**。Intel 平台上这类信号的表现就是 **BD PROCHOT**——一根直接进 CPU 的"外部请求降频"信号脚。

这是一条纯硬件的闭环：VRM 过热 → VRM 控制器拉信号 → CPU 立刻降频。**全程不需要 SMC 读任何温度**，SMC/操作系统只是事后收到"供电侧出问题了"的通知，把它转述成 PLIMIT 和热压力。

一个类比：汽车的油温传感器坏了，但油压表还在。油温过高时油压会掉，ECU 看到"油压异常"照样限扭保护——司机从仪表上看不到油温多少度，只知道车没劲。A2141 上：SMC 看不到 VRM 温度，但看得到"供电侧在报警"，照样压功率；你从 MacState 上看不到"VRM 95°C"，只看到"当前限制 31%"。

**② SMC 监控的是"后果"而不是"原因"**

- **输入电压跌落**：VRM 吃紧时母线电压会被拉低（机器里有 `VacVoltageLimit` 等电压监控），电压一跌就是供电不足的直接证据；
- **功率轨迹**：实测里 125W 的爆发几秒内就触发钳制——SMC 对"短时间功率冲太高"有直接反应，不需要等任何东西热起来；
- **周边板级测点**：`TC0P`（CPU 供电区近旁）、`TGVP`（独显供电区）虽然不是 VRM 结温，但能反映供电区*附近*的板温趋势。

**③ 时间积分与经验曲线**

SMC 固件里大概率还有"持续高功率运行多久后主动降压降频"的预防性策略（从实测的"负载 40 秒后钳到 26%"这种渐进行为可以反推）。这同样不需要温度输入——功率×时间的累积本身就是热风险的代理指标。

所以准确的说法是：**SMC 读不到 VRM 的温度，但读得到 VRM 的"行为"（报警信号、电压、电流、功率）**。A2141 的问题恰恰是这种间接监控不够灵敏——等它反应过来时 VRM 已经很烫了，而恢复又保守（钳制黏几十分钟），形成了"温度看着不高、机器却卡很久"的体感。

### 邻近测点（TC0P/TGVP/TGVF）能信多少？——实测划出的边界

TC0P/TGVP 是焊在 PCB 表面的热敏电阻，量的是**板子铜箔那一点**的温度；发热体是 VRM 的 DrMOS/电感，热要走"结 → 封装 → 焊点 → 铺铜 → 板面"逐级降温。结论先说：**趋势可信，数值不可信，拿来做报警阈值尤其不可信**。

**梯度有多大**：外部实测推测 VRM 结温可破 100°C 时，TGVP 才 60~70°C——**结温与邻近板级测点的梯度约 30~50°C**，大电流瞬态时更大。梯度还随散热状态变化：原装黑胶带（隔热层）把热捂在元件上，梯度拉大；D 壳导热垫改装把热抽走，整个区域更凉更均匀，梯度缩小、测点读数更接近真实——但绝对值永远偏低。TGVF 是 TGVP 的滤波值，天然更滞后。

**本机压测数据验证出的三个"可信度边界"**：

- **TGVP：方向性可信。** 热浸泡组压测中 CPU 独自满载、独显几乎空闲，TGVP 仍在一分钟内从 61.6°C 爬到 65.5°C（CPU 的热顺着主板烤独显供电区，它感知到了）；且热浸泡组 TGVP 65.5°C → 被深度钳制、凉机组 54.8°C → 未被钳，方向完全一致。判断"供电区是否在积热"，用它。
- **TC0P：被数据证明不是钳制触发器。** 被深度钳制那次 TC0P 全程 ≤64°C，未被钳的凉机组反而冲到 72~75°C——若 SMC 按它钳制，凉的那次应该钳得更狠，实际相反。判断 CPU 钳制原因时别用它。
- **恢复行为同样证明决策不在测点**：负载一停，板级测点几分钟就回落（铜箔热容小、风道散热快），钳制却黏了 30+ 分钟。触发与解除都不以邻近测点为判据——与上文机制 ①（VRM 自身保护信号）吻合。

**使用建议**：把 TGVP/TGVF 当"供电区积热趋势计"——持续爬升 + MacState 限速段变红 = 供电侧问题；**不要**给它们设"XX°C 就不正常"的绝对阈值：测点显示 65°C 时结温可能已 100°C+，显示 75°C 时也可能啥事没有。

## 6. 为什么 CPU+独显同时负载最严重

三个原因叠加，全都指向供电和功率预算：

1. **两路大功率同时抽流。** CPU 睿频可到 55~65W，5500M 满载约 50~67W，再加平台本身 15~25W——**合计逼近甚至超过 100W 适配器的总预算**。SMC 必须在两个域之间抢预算，表现为 CPU、GPU 的 PLIMIT 交替下压（实测 GPU 一度被压到 7%）。
2. **两个 VRM 区在物理上互相加热。** CPU 供电区和独显供电区在主板上相邻，共用同一套散热风道。实测：**纯 CPU 满载、独显几乎空闲时，独显供电区测点 TGVP 依然从 61.6°C 一路爬到 65.5°C**——CPU 的热顺着主板烤独显的供电区。反过来独显满载时也会烤 CPU 供电区。两边叠加后，任何一个区先过热都会触发整机钳制。
3. **独显唤醒本身改变功率格局。** 外接屏幕/浏览器硬件加速会唤醒 5500M，独显一亮就多出一份功耗，而这台机器的上屏合成始终在核显上（独显渲染+核显合成同时吃电），更容易顶到功率墙。

这就是为什么"看视频没事、一开浏览器+直播+导出就卡"——单负载未必破墙，双负载必破。

## 7. MacRumors 上的 VRM 改装是怎么做的

外网验证最充分的硬件方案是 **VRM 导热垫改装**（VRM thermal pad mod），思路是把 VRM 的热量通过导热垫传导到铝制底壳（D 壳）上散掉：

**材料**

- 2~3mm 厚导热垫若干（社区常用 Laird HD90000，或 ARCTIC 等同厚度导热垫；太薄垫不满间隙，太厚顶壳）
- 撬片、Torx/十字螺丝刀（A2141 底盖为六角/梅花螺丝）

**步骤**

1. 关机断电，拆下底盖；
2. 找到**主板上的 CPU 供电区和独显供电区**——即电感+功率元件密集的区域（MacState"供电/VRM"组里 `TC0P`/`TGVP` 测点旁边就是这两个区）；
3. **关键一步：撕掉 VRM 区覆盖的黑色胶带。** 这层胶带是**隔热层**，不撕掉它导热垫基本无效（MacRumors 帖子里有用户没撕胶带，改装后零提升）；
4. 按元件高度剪导热垫（约 2~3mm），贴在 VRM 元件上，对准底壳对应位置——合盖后垫子被夹在元件与铝壳之间，把热量导到壳上；
5. 装回底盖，完成。

**实测效果与代价**

| 效果 | 数据 | 来源 |
|---|---|---|
| 持续功率墙抬高 | 整机（CPU+GPU）57W → ~64W | MacRumors 实测帖 |
| 导出不再掉速 | FCP 导出全程稳定 ~2.9GHz（改装前 3 分钟掉到 1.8GHz、整机 88W→60W） | xujiwei 博客 |
| 改装后风险 | **D 壳对应区域会明显发烫**（不宜放腿上）；拆盖影响保修 | — |

### 本机同日两组压测对照（2026-09-07 实测：同一台机器、同一套改装、同一个 100W 适配器）

本机的 D 壳导热改装（CPU/GPU/VRM 均贴垫导至铝壳）早已完成，所以下面早晚两组压测的硬件完全相同——**唯一差别是机身热状态**：凌晨组开测前机器已被高强度负载连烤一个多小时，晚间组开测前是轻负载凉机。

| 指标 | 凌晨组（热浸泡后） | 晚间组（凉机后） |
|---|---|---|
| 起始 TC0P / TGVP | 58°C / 61.6°C | 54°C / 49.8°C |
| 起始风扇 | 已钉 5600rpm | ~2950rpm |
| 持续 CPU 功耗（负载 45~72s 均值） | **19W**（深度钳制，允许功率 ~26%） | **62W**（峰值 72W，无深度钳制） |
| 整机输入功率 | 66W（被压） | **96~105W** |
| 钳制深度与时长 | cpu=31%/gpu=7% 黏 30+ 分钟 | 仅浅限（瞬时 4~13%），约 3 分钟归零 |
| CPU 板级测点 TC0P | ≤64°C（被钳住跑不起来） | 72~75°C（CPU 被允许真跑了） |

供电完全相同，持续可用功率却差 3.3 倍——**功率墙跟着机身热状态走，不跟供电走**。这就是"散热是约束"在本机上最直接的证据：电源能提供的电没变过，变的是机壳里存了多少热。

### 外部"改装前 vs 改装后"对照（同一台机器）

- **知乎·刘子昂**（i9-9980HK + 5500M；换硅脂 + VRM 导热垫至 D 壳 + **铲掉 D 壳内侧石墨隔热层**，注意垫子不要连接热管否则反优化）：整机瞬时功耗 **120W → 160W**（可维持 3-6 秒）；双烤 CPU 稳住 45W TDP / 全核 ~2.8GHz；接 4K 屏 + 独显时 Cinebench R23 **7100 → 7900**；低负载风扇 2300-2500rpm 静音。https://zhuanlan.zhihu.com/p/450512435
- **今日头条·BootCamp 实测**（i9-9880H + 5500M 8GB）：GPU PPT Limit 阶梯式钳制 **50→40→30→15W**，逐项排除电源（原装 96W）、CPU（PL1 25W 时 70-80°C 无热降频）、驱动后定位 VRM 过热；**同一台机器只把风扇从自动改为固定 4500-5500rpm，PPT 立刻稳在 50W、GPU 功耗稳定 40-45W**——不动任何供电环节，只加强散热，钳制消失。https://www.toutiao.com/article/7650411212034802211/
- MacRumors VRM-mod 帖：整机持续功耗墙 57W → ~64W。

三组对照共同指向同一结论：**瓶颈在散热侧，功率墙只是散热能力在系统里的投影**。这也解释了为什么换 140W 适配器无效：A2141 的 USB-C 输入上限是 ~96-100W（PD 3.0，20V 档；28V/5A EPR 属 PD 3.1，2021+ 机型才有），而且未改装机器的整机瞬时消耗本来就能到 120W+（本机实测 124.9W，改装后社区实测 160W）——限制从来不是"电不够"。

本机数据还有两条佐证：

1. 3 天历史数据里整机瞬时消耗最高 **137~147W**——这是"适配器 ~100W + 电池同时放电 30~40W"的**合计消耗**，也就是"140W"说法的真实来源（消耗能力 ≠ 输入能力）；
2. xcpm 的供电/IO 限频通道在这台机器上**从未触发过**（`machdep.xcpm.io_control_engages = 0`），即适配器输入侧从未成为限制者——被按住的一直是 SMC 功率策略（散热的代理）。

若仍考虑大功率充电器：>60W 必须配带 **E-Marker 芯片**的 USB-C 线，否则按 60W 协商（维修论坛反复强调 "cable is VERY important"）；140W 充电器对 A2141 的唯一实际意义是充电余量与断电池 DFU 维修场景。

**不想/不能拆机的替代方案与日常运维**（效果递减）：

| 方案 | 效果 | 代价/备注 |
|---|---|---|
| **手动风扇控制**（Macs Fan Control 固定转速） | 头条实测：同一台机器自动挡 GPU PPT 掉到 15W，**固定 4500-5500rpm 后 PPT 稳在 50W、GPU 功耗稳定 40-45W**——不动任何硬件就消除钳制 | 噪音。日常 4500rpm、夏季 5000-5500rpm。与 D 壳导热互补：垫子负责把热带出去，风扇负责不让热积在壳里 |
| 软件限频/关睿频（Turbo Boost Switcher；BootCamp 下 ThrottleStop PL1=20-25W / PL2=28-33W） | 确定有效：不冲功率墙就不触发钳制，长期反而更稳 | 牺牲峰值性能（有 2018 机型"限频后反而更快"的实测） |
| 强力外冷（散热底座+垫高） | 有效，配合软件限频可稳 65~85W | 有噪音，治标 |
| 清灰 + 更换导热材料（CPU/GPU 可用 PTM7950 相变片） | CPU 侧改善约 7%（2018 数据）；**对 VRM 掉功率帮助有限**——头条结论："清灰有帮助但解决不了 VRM 热保护，风扇策略才是关键" | 需拆机 |
| 重置 SMC/PRAM | 对个别"卡死在低频"的状态一次性有效 | 非通解 |

三个使用场景备注：

- **5600M 顶配**（HBM2 显存）内部设计有改进，VRM 问题相对轻——但依然是同代散热思路；
- **外接双显示器**时 dGPU 常驻 ~20W，还可能触发雷电口附近温度传感器的另一路降频——双屏用户优先上"固定风扇"这条；
- 导热垫厚度社区有两派（MacRumors 2~3mm / 知乎 0.5~1.5mm 需压合紧密不伤元件）——按实际间隙选，以合盖后压实、不顶壳为准。

另外记一笔历史：2018 款 15"（A1990）的初代 i9 降频门最终由 Apple 以"固件缺少数字密钥"名义发补丁修复并致歉；**A2141 没有得到任何官方承认或维修计划**，上述方案全部来自社区。

## 8. MacState（v1.9.1+）怎么看这个状态

- **菜单栏限速段**：显示瞬时 CPU PLIMIT。低于 95% 且 CPU 负载 ≥50% 时变红（真·正在降频）。
- **点限速段弹出面板**：顶部是"当前限制（CPU/GPU）+ 近期平均 + 热状态"，下方全部温度测点。**独显被压（比如 GPU 7%）只有这里能看到**。
- **历史曲线**：限速/功率/温度/负载 10 秒粒度存 3 天，回看"什么时候被钳过"一目了然。

典型模式对照：

| 现象 | 结论 |
|---|---|
| 当前限制 100%，负载高 | 正常满血 |
| 当前限制 <100% 且负载高 | 正在被钳制（看功率曲线是否冲高过） |
| 当前限制 <100% 但负载很低 | 钳制残留，等它恢复；独显唤醒/大功率会立刻恶化 |
| 近期平均 ≠ 当前限制 | 两者差值大说明刚发生过（或刚解除）钳制 |

## 9. 诊断速查

```bash
# 当前钳制状态（MacState 显示的就是这两个来源）
pmset -g therm                      # CPU_Speed_Limit：<100 = OS 侧看到钳制
sysctl machdep.xcpm.cpu_thermal_level   # 热压力指数，>100 进入 Heavy 区间

# SMC 功率/温度键读取（MacState 的同款方法）
# PSTR=系统功率 PCPC=CPU功率 PCPG=GPU功率 TC0P=CPU供电区板温 TGVP=独显供电区板温

# 持续观察钳制行为
pmset -g thermlog                   # 持续输出 CPU_Speed_Limit 变化

# 需要管理员权限的深度工具
sudo powermetrics --samplers thermal,sfi,cpu_power   # 热压力 + SFI + 功率明细

# Boot Camp 双系统下
# HWiNFO/ThrottleStop 可直接看 BD PROCHOT 是否触发（§5 机制 ① 的直接证据）

# MBP16,1 实测不存在的键（任何工具读到 "--" 属正常）：
#   TC0D / TC0c / TC1c（CPU die 温度——只有板级测点 TC0P）
#   TG0D、MSIm、MSTc（瞬时 PLIMIT 键——瞬时限制只能走 PLIMIT 命令 selector 11）
```

本文实测所用方法：编译一个小 CLI 直接调 MacState 的 `SMCService`（源码在仓库 `MacState/Core/SMCService.swift`），每秒轮询上述键；PLIMIT 通过 SMC 用户客户端 selector 11 读取。
